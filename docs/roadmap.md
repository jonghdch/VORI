## 이 문서가 필요한 이유

VORI 의 중요한 설계 결정 몇 가지가 **코드에만 있고 문서에 없다.**

과지출에 감점을 주지 않는 것, AI 가 이유를 물은 뒤에 판정하는 것, 잠긴 상품을 숨기지 않는 것 —
전부 의도한 선택인데 기록해 두지 않으면 발표에서 *"그냥 그렇게 만든 것"* 으로 보인다.
심사위원이 *"과지출을 봐주는 게 너무 관대한 거 아닌가요?"* 라고 물었을 때 그 자리에서
논리를 만들어 내려 하면 늦다.

**이 문서의 절반은 이미 구현된 것의 근거고, 절반은 아직 안 한 것이다.** 둘을 섞지 않는다.

> ⚠️ 아래에 인용한 외부 앱들의 기능은 **직접 확인한 것이 아니다.** 앱은 계속 바뀐다.
> 보고서나 발표에 인용하기 전에 그 시점에 다시 확인할 것.
> 실제로 `지갑펫` 을 기억에 의존해 "직접 경쟁 앱" 으로 과대평가했다가
> 스토어를 열어 보고 정정한 적이 있다([`market-research.md`](market-research.md)).

## 1. 설계 철학 — 벌을 주지 않는 가계부

### 문제

가계부 앱이 죽는 방식은 대개 이렇다. 과소비한 달에 앱을 열면 미뤄왔던 현실을 마주하게 된다.
그래서 **과소비한 달에 앱을 열지 않게 된다.** 정작 제일 필요한 순간에 사용하지 않는다.

돈 문제에는 낙인이 있다. 빚, 과소비, 가난은 부끄러운 것으로 취급된다.
**언어 공부를 안 한 건 멋쩍고 말 일이지만 돈 관리를 못한 건 숨기고 싶은 일이다.**
그래서 언어 학습 앱에서 통하는 압박이 가계부에서는 이탈로 이어진다.

경쟁 앱 `지갑펫` 의 첫 문장이 *"돈 쓸 때마다 나를 혼내는 가계부는 그만!"* 인 것도 같은 관찰이다.

### VORI 의 선택 — 이미 구현돼 있다

| 결정 | 코드 |
|---|---|
| 과지출에 **감점이 없다.** 보상이 없을 뿐이다 | `stat_delta = max(saved, 0)` |
| 이유가 인정되면 **오히려 보상한다** (경조사·응급·자기투자) | `AiInquiryService` 코인 +100 · 스탯 +10 |
| 실패의 대상이 사용자가 아니라 **펫이다** | 과소비 → "네가 잘못했다" 가 아니라 "펫 스탯이 안 올랐다" |
| AI 가 **판단을 앞세우지 않는다** | 질문 프롬프트에서 긍정 전제·나무람·감탄사 금지 |
| 일일 코멘트가 **음수를 실패로 전제하지 않는다** | 사유를 모르므로 반성을 요구하지 않는다 |

> ⚠️ **2026-10-01 기준, 위 표의 1·2행은 main 코드와 다르다.** #56 에서 지출 저장 때의 절약 보상
> (`stat_delta`)과 AI 인정 보상(코인 +100 · 스탯 +10)이 빠지고 **하루 판정 보상**
> (초록 코인 500 · 스탯 4종 각 +11 / 회색 250 · +6 / 빨강 100 · +2)으로 바뀌었다.
> "과지출은 감점 없이 무보상" 은 그대로지만, **이유가 인정돼도 보상이 달라지지 않는다**(7절 참조).
> 이 구조를 유지할지 되돌릴지 **팀 결정 대기** — 결정 뒤에 이 표와 아래 "예상 질문" 답을 고친다.
> 그 전까지 발표·보고서·브로셔에 이 표를 그대로 인용하지 않는다.

### 선례

- **YNAB** 의 네 규칙 중 *"Roll with the punches"* — 예산을 넘기면 벌을 주는 대신 다른 항목에서
  옮겨 오게 한다. **계획이 바뀌어도 실패가 아니라고 제품 규칙에 박아 둔 사례**다.
  VORI 의 인정 보상이 같은 사고방식이다.
- **Finch** — 셀프케어 앱. 작은 일을 하면 새가 자란다. 며칠 빠져도 **새가 죽지 않는다.**
  정신건강이라는 민감한 도메인에서 압박을 못 쓰는 조건이 돈과 같다.
- **Forest** — 집중 앱. 앱을 나가면 나무가 죽는다. *"네가 실패했다"* 가 아니라
  *"나무가 죽었다"* 다 — **대상을 사물로 옮겨 자책을 줄인다.** VORI 의 펫이 같은 역할이다.

### 예상 질문에 대한 답

> **"과지출을 인정해 주는 건 너무 관대한 것 아닌가요?"**

관대함이 아니라 **선별**입니다. 경조사·응급·자기투자만 인정하고 충동구매(`IMPULSE`)와
사교 지출(`SOCIAL`)은 인정하지 않습니다. 실측에서 *"그냥 갖고 싶어서"*, *"스트레스 받아서"*,
*"세일하길래"* 세 답변 모두 `IMPULSE` 로 분류되어 RED 가 유지되고 보상이 나가지 않았습니다.

그리고 **벌을 주는 가계부는 과소비한 달에 사용자를 잃습니다.** 기록이 끊기면 어떤 기능도
소용이 없으므로 이탈을 막는 것이 우선입니다.

## 2. 마찰 감소와 AI의 역할

### 한계를 먼저 인정한다

토스·뱅크샐러드의 진짜 무기는 펫이 아니라 **자동 수집**이다. 계좌·카드를 연동해 기록이 저절로 쌓인다.
VORI 는 전부 손으로 입력해야 한다. **가계부가 버려지는 1번 이유가 "귀찮아서" 인데 VORI 는 그 지점에서 제일 약하다.**

오픈뱅킹 연동은 졸업작품 범위 밖이다(금융 API 심사·보안 요구사항).

### 그래서 영수증 OCR 이 기능 하나가 아니다

**자동 수집의 부재를 방어하는 유일한 마찰 감소 수단**이다. 사진 한 장으로 상호·날짜·금액·품목이
채워진다. 2026-09-10 에 프론트 진입점을 붙여 실제로 동작한다(`1a2558c`).

### AI 는 대체하지 않고 초안을 만든다

| 단계 | AI | 사람 |
|---|---|---|
| 영수증 | 값을 읽어 행에 채운다 | 확인·수정 후 저장 |
| 카테고리 | 임베딩으로 자동 분류 | 틀리면 바꾼다 |
| 과지출 | 이유를 **묻는다** | 답한다 |
| 판정 | 답변을 분류한다 | 결과를 받는다 |

**Copilot·Monarch 계열이 쓰는 구조**다. 자동화가 결정을 빼앗지 않고 초안을 만든다.
VORI 에서는 이 구조가 특히 중요하다 — 판정이 사용자의 삶에 대한 평가이기 때문에,
**AI 가 단독으로 결론 내리면 안 된다.**

## 3. 향후 확장 ① 소비 패턴이 펫을 결정한다

### 지금의 약점

가챠가 **순수 랜덤**이다. *"왜 가계부 앱에 뽑기가 있나요?"* 라는 질문에 지금은
"게임 요소" 말고 답할 말이 없다. 가계부와 육성이 **코인으로만** 연결돼 있다.

### 제안

알을 깔 때 **그 달의 소비 구성**이 등장 확률에 반영되게 한다.

```
식비 비중이 높았던 달      먹는 것에 반응하는 종족 확률 ↑
문화생활 비중이 높았던 달   지능 계열 종족 확률 ↑
교통 비중이 높았던 달      지구력 계열 종족 확률 ↑
```

**Pokémon Sleep** 이 수면 패턴에 따라 모이는 포켓몬 타입을 바꾸는 방식이다.

### 왜 이게 중요한가

가계부와 펫이 **처음으로 인과로 연결된다.** "내 소비 습관이 펫의 종류를 바꾼다" 가 되면
기록하는 행위 자체가 육성의 일부가 된다. 위 질문에 대한 답이 *"게임 요소라서"* 에서
*"소비 습관을 시각적으로 반영하는 페르소나"* 로 바뀐다.

### 구현 난도

낮은 편이다. `expenses` 에 카테고리별 집계가 이미 있고 `EggGrade` 의 확률 표에
가중치를 얹는 구조라 스키마 변경이 크지 않다. **11/4 최종발표에 넣을 수 있으면 최선**(6절 시점표·7절 마감표).

## 3-B. 향후 확장 ①-b 펫에게 이름을 지어준다

### 지금의 약점

**펫에 이름이 없다.** 알을 까면 종족명(`강아지`·`사슴`)이 그대로 화면에 뜨고, 사용자가 부를 이름을
정하는 단계가 없다. 시장 리서치의 결론이 *"펫 육성 자체는 차별점이 아니다"* 였는데, 그나마 애착을
만드는 값싼 장치 하나를 안 쓰고 있는 셈이다. 다마고치부터 포켓몬까지 **이름을 짓는 순간 대상이
'개체' 가 된다.**

### 먼저 정해야 할 것 — 보리와 펫의 역할 분리

지금 "보리" 는 두 자리에 동시에 쓰인다. 홈의 고정 문구(*"매일 0시에 보리가 소비 검사를 시작해요"*)에서는
**앱을 안내하는 마스코트**이고, 펫이 없을 때의 표시 이름(`activePet?.speciesName ?? "보리"`)에서는
**키우는 대상**이다. 사용자가 펫 이름을 직접 지으면 *"내 펫은 콩이인데 왜 보리가 검사하지?"* 가 된다.

```
보리   앱 전체를 안내하고 소비를 검사하는 시스템 AI (마스코트). 사용자가 이름을 바꿀 수 없다
펫     사용자가 이름을 지어 키우는 반려 캐릭터. 분양하면 떠나고 새로 받는다
```

**이 분리를 먼저 문구에 반영해야 한다.** 홈의 펫 없을 때 폴백을 "보리" 로 두면 경계가 다시 흐려진다.

### 화면별 표시 기준

| 화면 | 표시 | 왜 |
|---|---|---|
| **도감**(`PetDexPage`) | **종족명 고정** | 도감은 "이 세계에 어떤 종이 있는가" 를 보는 곳이다. 남의 별명이 들어갈 자리가 아니고, 수집 진행도도 종 기준으로 센다 |
| 마이룸 | **별명** (종족명은 작게 병기) | 매일 보는 화면이라 애착이 쌓이는 자리다 |
| 펫 이력 | **별명** | "콩이를 9,213 코인에 분양" 이 기억으로 남는다 |
| 분양 확인창 | **별명** | *"콩이를 분양할까요?"* — 망설이게 만드는 것이 이 창의 목적이다 |
| 개봉 결과 카드 | 종족명 → **이름 입력** | 태어난 직후가 이름을 짓기에 가장 자연스러운 순간이다 |

### 구현 난도

중간 정도다. **`pets` 테이블에 이름 컬럼이 없고**(V1 이후 이 테이블을 건드린 마이그레이션도 없다),
펫 API 는 조회·목록·분양 세 개뿐이라 **쓰기 엔드포인트를 새로 만들어야 한다.**

```
마이그레이션   pets 에 nickname VARCHAR NULL 추가
백엔드        Pet 엔티티 · PetResponse 필드, PATCH /api/pets/{id}/name
프론트        개봉 결과 카드(입력) · 마이룸 · 펫 이력 · 분양 확인창(표시)
```

별명이 비어 있으면 종족명으로 떨어지게 하면 **기존 펫도 마이그레이션 없이 그대로 보인다.**

> ⛔ **중간발표(9/30)에는 넣지 않기로 했다(2026-09-23).** 손댈 곳이 다섯 군데라 리허설을 처음부터
> 다시 검증해야 하고, 무대에서 타이핑이 한 번 더 늘어난다. 각본 1번에서 "결혼식 축의금" 을 정확히
> 쳐야 하는 부담이 이미 있다. **최종발표(11/4) 대상으로 남긴다.**

> ✅ **구현됨 — #66 (2026-09-30).** 컬럼 이름은 `nickname` 이 아니라 `pets.name`(VARCHAR(10), V25),
> 엔드포인트는 `PUT /api/pets/{id}/name`. 이름 없는 펫이면 모든 화면에 **닫을 수 없는 이름 짓기 팝업**
> (`PetNameGate`)이 떠서, 알 개봉 직후·시작 펫·기존 펫 모두 이름을 받는다.
>
> **남은 것 — 보리 역할 분리(위 "먼저 정해야 할 것").** 지금도 "보리" 가 펫 자리에 쓰이는 곳이 있다:
> 홈에서 펫이 없을 때 이름 칸(`HomeDashboard` — `"보리"` 폴백), 가입 설문 목표 "보리 키우기"
> (`SignupProfilePage`·`OnboardingPage`), 이름 입력 예시 "예: 보리"(`PetNameGate`).
> 마스코트 자리("보리가 소비 검사를 시작해요", "보리가 오늘 소비를 분석해요")는 그대로 둔다.
> 문구를 어떻게 바꿀지는 팀이 정한다.

## 4. 향후 확장 ② 프라이버시가 보호되는 응원망

### 하지 않을 것부터 정한다

**금액 기반 리더보드는 만들지 않는다.** 절약액을 나란히 세우면 사실상 **소득을 비교**하게 된다.
100만원 버는 사람과 500만원 버는 사람의 절약액을 같은 표에 두는 것은 잔인하다.
Strava·듀오링고가 비교하는 것도 결과가 아니라 **노력(거리·XP)** 이다.

**사유(판정 결과)도 공유하지 않는다.** 금액을 가려도 `경조사` 가 떴다는 것은 누가 결혼했거나
돌아가셨다는 뜻이고 `응급` 은 병원에 갔다는 뜻이다. **금액보다 더 사적이다** — 건강과 가족사가 드러난다.

### 공유해도 되는 것

```
안전   연속 기록일수 · 칭호 획득 · 기록 건수 · 펫 분양 완료      행위만 드러남
위험   금액 · 절약액 · 사유 카테고리 · 판정 결과              삶이 드러남
```

**Strava 의 Kudos** 처럼, 친구의 피드에 *"7일 연속 기록"*, *"'기록의 시작' 칭호 획득"* 만 뜨고
거기에 응원을 보낸다. 돈은 한 글자도 나오지 않는다.

- OCR은 완료: Google Vision이 아니라 Gemini 이미지 입력으로 가기로 한 설계대로

### 확정 5가지 (신뢰도 높음)

1. 다시 불러오는 장치가 없다 — PWA + 저녁 회고 알림이 가장 직접적인 재진입 수단.
2. 첫 1분이 비어 있다 — 온보딩으로 기준선 채우기 + 게스트 데모.
3. 보상이 앱 밖에서 가치가 없다 — 코인뿐. 절약액을 원화로 크게 + 목표 연결.
4. 퍼질 길이 없다 — 금액·사유 가린 펫·판정 공유 카드. 4절 "응원망" 원칙(행위만 공유) 그대로.
5. 입력이 귀찮다 — 이미 2절의 인정된 약점. OCR은 끝났으니 남은 건 분류 정확도·확인 흐름.

| **변명으로 다 넘어갈 우려** | 1 | "큰 지출을 초록으로 바꿔 주는 기준을 잘 잡아야" | 1절 "예상 질문" 답 그대로 — 경조사·긴급·자기투자만 인정, 충동·사교는 인정 안 함. 모호한 답("그냥 썼어")도 다시 묻지 않고 분류하며, 기타·충동은 판정을 바꾸지 않아 빨강이 유지된다(`AiInquiryService.computeSignalFinal`). **11/4 에 "그냥 갖고 싶어서" → 빨강 유지 장면을 직접 보여 준다** |
| **소비 성향별 다른 펫** | 1 | "소비 성향에 따른 다양한 펫" | **3절 그대로다** → "가능하면" 에서 **권장** 으로 올리는 근거 |
| **입력 편의** | 2 | "계좌이체·카드 결제 내역 캡처도 불러오기", "입력하면 다음 칸으로 자동 포커스" | 캡처 인식은 영수증 OCR 프롬프트를 넓히면 된다(소). 자동 포커스는 화면 작업(소) |
| **기능 확장** | 2 | "구독비 같은 고정지출 관리·추천 카드", "여행·컴퓨터처럼 큰돈을 모으는 저축 카테고리" | 목표 저축은 **백엔드 API(`/api/goals`)가 이미 있고 화면이 없다** → 화면만 붙이면 된다. 고정지출은 반복 결제 표시(`is_recurring`)가 있다. 카드 추천은 범위 밖(금융상품 추천) |
| **발표 방식** | 1 | "시연을 영상으로 준비한 게 아쉽다" | 교수님 피드백과 같음 → 라이브 시연 |
| 긍정 | 7 | 깔끔하다, 간편하다, 게이미피케이션이 좋다, 시연을 보니 다 필요한 기능이다, 최종발표가 기대된다 | — |

### 우선순위 제안 (2026-10-01, 황채린 — 팀 회의에서 확정)

```
~10/7    보상 구조 결정(신동엽·정다은) · 브로셔 팀 업로드(10/7)
10/8~    결정에 따라 판정 문제 2개 수정 또는 보상 복구 → 시드 복구 → 성장 밸런스 확인
         보리 문구 분리(3-B) · 펫 코멘트에 지출 사유 전달(황채린, #72)
         3절(소비 패턴 → 펫) 착수 — 상호평가 근거로 "가능하면" → 권장
         작은 것: 결제 내역 캡처 인식 · 입력 자동 포커스 · 목표 저축 화면(API 있음)
~11/3    11/4 시연 준비 — 라이브 흐름 + 백업 영상 재녹화, 구간별 대본, 타이머 리허설
         시연에 넣을 장면: 이유 답변 → 판정·보상 변화(차별점), "그냥 갖고 싶어서" → 빨강 유지, 출석
11/5~    클라우드 배포 + QR → 게스트 데모 (11/12)
```

- 담당은 팀 회의에서 정해 이 표에 적는다.
- 3절을 권장으로 올리는 이유: 상호평가에서 가장 많이 나온 "왜 펫인가 · 토스와 무엇이 다른가" 와
  "소비 성향별 다른 펫" 에 한 번에 답한다. 구현 난도는 3절 본문대로 낮은 편이다.
- 중간발표 전 "발표 후 논의" 로 미뤘던 **콜드스타트 판정 규칙(첫 5건 평균 ±20%, #33 에서 제외)** 은
  온보딩 기준선이 같은 문제(처음 5건 판정 공백)를 풀었으므로 **더 다루지 않는 것을 제안**한다.

### 화면 표기 통일 — 팀 회의 안건

같은 값을 화면마다 다른 이름·색으로 부른다. 사용자는 둘이 같은 것인지 알 수 없다. 어느 쪽으로 맞출지 정한다.

| 값 | 화면 | 지금 표기 |
|---|---|---|
| 펫 등급 S/A/B/C | 도감·스토리(`petCatalog.js`) | 레전드 / 에픽 / 희귀 / 일반 |
| | 상점 확률(`ShopPage`) | S / A / B / C |
| | 상점 소개·개봉 결과·업적·칭호 "행운아" | S등급 … C등급 |
| 판정 GRAY / RED | 판정 결과 화면(`JudgmentResults`) | 노랑 · 보통 / 주황 · 주의 (색도 노랑·주황) |
| | 가계부 표·상세(`WalletPage`)·이용약관 | 중립 / 비합리적 (색은 회색·빨강) |
| | 랜딩 페이지 | 중립 / 과소비 |
| | 졸업작품집 브로셔 | 회색 / 빨강 |

- 데이터(등급·판정 값)는 그대로 두고 **화면 문구만** 바꾸는 일이라 마이그레이션은 필요 없다.
  칭호 이름·설명("S등급 펫 획득")은 DB(`titles`)에 있어 관리자 화면에서 바꿀 수 있다.
- 종·등급 개편(V16·V17) 정합성은 10/1 에 확인했다 — 시더·마이그레이션 경로·도감 목록·펫 그림·로컬 DB 16종이 모두 일치. 남은 문제는 이 표기뿐이다.
