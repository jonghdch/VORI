# 회원가입·소비 프로필 수집 흐름 설계

> 회원가입 중 사용자 소비 패턴과 습관을 5단계 선택형으로 수집하고, 가입 완료 직후 온보딩 튜토리얼로 이어지는 흐름.
> 목표는 개인정보를 많이 받는 것이 아니라, 신규 사용자가 첫 지출부터 VORI 의 "내 기준 판정"을 이해하게 만드는 것이다.
>
> 작성 기준: 2026-09-23. 연결 문서: [`tutorial-flow.md`](tutorial-flow.md)

## 설계 목표

회원가입은 계정 생성만 끝내는 화면이 아니라, VORI 의 판정 기준을 만드는 첫 경험이어야 한다. 다만 가입 단계가 길어지면 이탈이 커지므로 모든 문항은 선택형으로 만들고, 사용자가 숫자를 직접 계산하지 않아도 답할 수 있게 한다.

핵심 목표는 네 가지다.


| 목표         | 설계 방향                                                  |
| ---------- | ------------------------------------------------------ |
| 첫 판정 품질 보완 | 신규 사용자의 `sample_count < 5` 구간에서 fallback 만 보이는 문제를 줄인다 |
| 입력 부담 최소화  | 자유 입력 없이 5단계 선택형으로 끝낸다                                 |
| 사용자 신뢰 확보  | 왜 묻는지 각 단계에서 짧게 설명한다                                   |
| 온보딩 연결     | 가입 완료 후 바로 기능 설명이 아니라 첫 기록 행동으로 이어진다                   |


## 전체 흐름

```text
/signup
  → 1. 계정 정보 입력
  → 2. 약관 동의
  → 3. 소비 프로필 5단계
  → 4. 가입 완료 + 자동 로그인
  → 5. 온보딩 튜토리얼
  → 6. 첫 지출 기록 또는 홈
```

사용자가 보기에 회원가입은 하나의 흐름이어야 하지만, 구현상으로는 `계정 생성`과 `소비 프로필 저장`을 분리한다. 계정 생성이 성공했는데 프로필 저장이 실패하면 계정을 롤백하기보다, 로그인 후 온보딩에서 다시 이어서 받는 쪽이 복구가 쉽다.

## 화면 구조

### Step 1 — 계정 정보

현재 회원가입 화면의 기본 필드를 유지한다.

수집:

- 닉네임
- 이름
- 이메일
- 비밀번호

버튼:

- `다음`

검증:

- 이메일 형식
- 비밀번호 규칙
- 필수 값 누락

### Step 2 — 약관 동의

현재 필수 약관 구조를 유지한다.

수집:

- 서비스 이용약관 동의
- 개인정보 처리방침 동의
- 마케팅 수신 동의는 선택

버튼:

- `소비 기준 설정하기`

주의:

- 소비 프로필 문항이 개인정보 처리 목적에 포함되어야 한다.
- 민감정보처럼 보일 수 있는 표현은 피한다. `소득 수준`보다 `한 달 사용 가능 금액`이 낫다.

## 소비 프로필 5단계

모든 단계는 카드형 단일 선택이다. 각 단계는 4개 선택지를 기본으로 하고, 사용자가 모르면 `잘 모르겠어요`를 선택할 수 있게 한다. `잘 모르겠어요`는 판정 기준을 만들지 않고 기본값을 쓴다.

### Step 3-0 — 월 수입 (필수)

숫자 입력 한 칸. 선택형 5문항과 달리 **건너뛸 수 없다.** 쇼핑·문화·생활비 타입의 초기 판정 기준선을
월 수입에서 유도하기 때문이다(`BaselineSeeder`: 평균 = 수입 × 타입별 비율, RED 경계 = 수입 × 타입별 비율,
편차는 두 값과 `z_red` 로 역산). 식비는 아래 3-2 의 한 끼 답을 우선 쓴다.

- 저장: `users.monthly_income` (프로필 설정과 같은 컬럼 — 나중에 거기서 수정 가능)
- 수정 시: 실제 지출이 없는 타입만 기준선을 다시 잡는다

### Step 3-1 — 생활비 규모

사용자에게 보이는 질문:

```text
한 달에 자유롭게 쓸 수 있는 돈은 어느 정도인가요?
```

선택지:

- `20만원 이하`
- `20만~40만원`
- `40만~70만원`
- `70만원 이상`
- `잘 모르겠어요`

활용:

- 전체 소비 민감도 초기값
- 월 예산 기본값 제안
- 과소비 안내 문구 강도 조절

주의:

- `월소득`이라고 묻지 않는다. 학생 사용자에게 장학금, 용돈, 아르바이트비가 섞여 있을 수 있다.

### Step 3-2 — 식비 기준

사용자에게 보이는 질문:

```text
평소 한 끼에 얼마 정도 쓰나요?
```

선택지:

- `7,000원 이하`
- `7,000~10,000원`
- `10,000~15,000원`
- `15,000원 이상`
- `잘 모르겠어요`

활용:

- `ENERGY` 계열 기준선 초기화
- 첫 지출 예시 카테고리 추천

판정 예시:

- 사용자가 `7,000~10,000원`을 고르면 식비 계열의 초기 평균 후보를 `8,500원`으로 둔다.
- 첫 식비 지출이 `9,000원`이면 무조건 GREEN 으로만 처리하지 않고 "평소 범위와 비슷해요" 같은 안내를 줄 수 있다.

### Step 3-3 — 자주 쓰는 영역

사용자에게 보이는 질문:

```text
요즘 가장 자주 돈을 쓰는 곳은 어디인가요?
```

선택지:

- `식비·카페`
- `쇼핑·뷰티`
- `문화·여가`
- `교통·생활비`
- `잘 모르겠어요`

활용:

- 첫 기록 튜토리얼 예시 문구 개인화
- 홈 체크리스트 첫 CTA 문구 개인화
- 사용자가 선택한 영역의 카테고리를 지출 작성 화면에서 먼저 추천

매핑 후보:


| 선택지    | 우선 추천 statType |
| ------ | -------------- |
| 식비·카페  | `ENERGY`       |
| 쇼핑·뷰티  | `CHARM`        |
| 문화·여가  | `IQ`           |
| 교통·생활비 | `ENDURANCE`    |


### Step 3-4 — 소비 습관

사용자에게 보이는 질문:

```text
내 소비 습관에 가장 가까운 건 무엇인가요?
```

선택지:

- `계획한 것만 사는 편`
- `필요하면 바로 사는 편`
- `할인이나 이벤트에 약한 편`
- `기분에 따라 쓰는 편`
- `잘 모르겠어요`

활용:

- AI 질문 톤 조절
- 충동 소비 의심 시 문구 개인화
- 목표 추천

주의:

- 사용자를 비난하는 표현을 쓰지 않는다.
- 선택 결과로 즉시 불이익을 주지 않는다. 이 답변은 판정 확정값이 아니라 질문 우선순위와 안내 문구에만 쓴다.

### Step 3-5 — 이번 달 목표

사용자에게 보이는 질문:

```text
이번 달 VORI 에서 가장 해보고 싶은 건 무엇인가요?
```

선택지:

- `지출 기록 습관 만들기`
- `식비 줄이기`
- `충동구매 줄이기`
- `보리 키우기`
- `잘 모르겠어요`

활용:

- 홈 체크리스트 문구
- 첫 목표 생성 후보
- 온보딩 마지막 CTA 결정

CTA 예시:


| 선택지          | 온보딩 마지막 버튼   |
| ------------ | ------------ |
| 지출 기록 습관 만들기 | `첫 지출 기록하기`  |
| 식비 줄이기       | `오늘 식비 기록하기` |
| 충동구매 줄이기     | `최근 소비 돌아보기` |
| 보리 키우기       | `보리 만나러 가기`  |


## 가입 완료 후 온보딩 연결

소비 프로필 저장이 끝나면 사용자를 바로 홈으로 보내지 않는다.

```text
소비 기준 설정 완료
  → 시작 펫 확인
  → VORI 판정 방식 2장
  → 첫 지출 기록 CTA
```

### 완료 화면

사용자에게 보이는 문구:

```text
내 소비 기준이 준비됐어요.

이제 첫 기록을 남기면
보리가 오늘 소비를 내 평소 기준으로 살펴봐요.
```

버튼:

- `첫 지출 기록하기` → `/wallet/new`
- `홈으로 가기` → `/home`

### 온보딩 튜토리얼과의 관계

기존 [`tutorial-flow.md`](tutorial-flow.md)의 `소비 기준선 설정` 단계는 회원가입 안으로 이동한다. 따라서 가입 직후 온보딩은 설문을 다시 묻지 않고, 사용자가 방금 답한 기준을 요약해준다.

예시:

```text
평소 한 끼 기준은 7,000~10,000원으로 볼게요.
처음 몇 번은 기록이 쌓이도록 부드럽게 판정해요.
```

## 저장 데이터 설계

회원가입 기본 정보와 소비 프로필은 저장 목적이 다르므로 테이블을 분리하는 것을 권장한다.

### 신규 테이블 후보 — `user_spending_profiles`


| 컬럼                    | 타입           | 설명                          |
| --------------------- | ------------ | --------------------------- |
| `user_id`             | BIGINT PK/FK | 사용자 ID                      |
| `monthly_budget_band` | VARCHAR(30)  | 생활비 규모 선택값                  |
| `meal_cost_band`      | VARCHAR(30)  | 한 끼 식비 선택값                  |
| `primary_spend_area`  | VARCHAR(30)  | 자주 쓰는 영역                    |
| `spending_habit`      | VARCHAR(30)  | 소비 습관                       |
| `monthly_goal`        | VARCHAR(30)  | 이번 달 목표                     |
| `baseline_applied`    | BOOLEAN      | `user_stat_stats` 초기값 반영 여부 |
| `created_at`          | DATETIME     | 생성 시각                       |
| `updated_at`          | DATETIME     | 수정 시각                       |


enum 을 코드에만 박아두기보다 DB에는 문자열 코드로 저장하고, 프론트 선택지는 별도 설정 JSON 또는 API 응답으로 내려주는 방식이 낫다. 선택지 문구는 발표/기획에서 자주 바뀔 수 있지만, 저장 코드는 오래 유지되어야 한다.

### 기준선 반영 방식

권장 방식은 `user_stat_stats`에 가짜 지출을 넣는 것이 아니라, 초기 통계값만 부드럽게 세팅하는 것이다.

```text
meal_cost_band = 7,000~10,000원
  → ENERGY mean_ema = 8,500
  → ENERGY stddev_ema = 2,000
  → ENERGY sample_count = 3
```

이렇게 하면 실제 지출 내역에는 사용자가 쓰지 않은 가짜 데이터가 생기지 않고, 첫 지출 판정에서만 기준선 부재 문제가 줄어든다.

주의:

- `sample_count`를 바로 5 이상으로 올리면 첫 기록부터 너무 단정적인 판정이 나올 수 있다.
- 초기값으로 만든 판정은 UI에서 "초기 기준"임을 부드럽게 보여주는 것이 좋다.
- 사용자가 `잘 모르겠어요`를 선택한 statType은 현재처럼 `sample_count = 0`에서 시작한다.

## API 설계 후보

회원가입 API에 모든 문항을 얹는 방법도 가능하지만, 유지보수와 실패 복구를 생각하면 분리 API가 낫다.


| 메서드  | 경로                                 | 설명                    |
| ---- | ---------------------------------- | --------------------- |
| POST | `/api/auth/signup`                 | 계정 생성. 기존 역할 유지       |
| POST | `/api/onboarding/spending-profile` | 5단계 답변 저장 + 초기 기준선 반영 |
| GET  | `/api/onboarding/status`           | 프로필 작성 여부, 튜토리얼 완료 여부 |
| POST | `/api/onboarding/complete`         | 온보딩 완료 처리             |


권장 요청 예시:

```json
{
  "monthlyBudgetBand": "BAND_20_40",
  "mealCostBand": "MEAL_7_10",
  "primarySpendArea": "FOOD_CAFE",
  "spendingHabit": "EVENT_SENSITIVE",
  "monthlyGoal": "REDUCE_IMPULSE"
}
```

응답 예시:

```json
{
  "profileCompleted": true,
  "baselineApplied": true,
  "nextPath": "/onboarding"
}
```

## 프론트 라우팅 설계

추천 라우트:


| 경로                | 역할             |
| ----------------- | -------------- |
| `/signup`         | 계정 정보 + 약관     |
| `/signup/profile` | 소비 프로필 5단계     |
| `/onboarding`     | 가입 직후 온보딩 튜토리얼 |
| `/wallet/new`     | 첫 지출 기록        |


가입 완료 후 분기:

```text
POST /api/auth/signup 성공
  → POST /api/auth/login 성공
  → /signup/profile
  → POST /api/onboarding/spending-profile 성공
  → /onboarding
```

로그인 복구 분기:

```text
로그인 성공
  → GET /api/onboarding/status
  → profileCompleted == false 이면 /signup/profile
  → tutorialDone == false 이면 /onboarding
  → 둘 다 완료면 /home
```

## UX 규칙

- 진행률은 `1/5`처럼 숫자로 보여준다.
- 각 단계는 질문 1개와 선택지 4\~5개만 둔다.
- 뒤로가기를 허용한다.
- 설문은 필수다. `나중에 하기`는 두지 않고, 설문을 마치기 전에는 로그인이 필요한 화면 어디로 가도 설문으로 돌아온다(`ProtectedRoute` 가 기본으로 확인). 모르는 항목은 `잘 모르겠어요`를 고르면 된다.
- 선택 즉시 다음 단계로 넘기지 말고 `다음` 버튼을 둔다. 실수 수정이 쉬워야 한다.
- 선택지는 사용자를 평가하거나 낙인찍는 표현을 피한다.
- 가입 완료 전에는 펫·가구·칭호 설명을 길게 넣지 않는다.

## 최소 구현 범위

중간/최종 발표 전 현실적인 최소 범위는 다음이다.

1. `/signup/profile` 5단계 선택형 화면
2. `user_spending_profiles` 저장
3. 식비 선택값을 `ENERGY` 초기 기준선에 반영
4. 가입 완료 후 `/onboarding`으로 이동
5. 온보딩 완료 후 `/wallet/new` 또는 `/home` 이동

확장 범위:

- 모든 statType 기준선 초기화
- 목표 자동 생성
- AI 질문 톤 개인화
- 프로필 재설정 화면

## 하지 말 것

- 회원가입 첫 화면에서 돈 관련 질문부터 하지 않는다.
- 실제 소비 내역을 가짜로 생성하지 않는다.
- 선택 결과로 빨간불 기준을 과하게 엄격하게 만들지 않는다.
- `월소득`, `재산`, `직업`처럼 답하기 부담스러운 질문을 필수로 만들지 않는다.
- 5단계 뒤에 추가 설문을 더 붙이지 않는다.
